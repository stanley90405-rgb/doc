TLS 1.3 API 介接連線確認與驗證操作手冊

適用對象：資安人員、系統維運（Infra/SRE）、後端開發（Java／Python／.NET）。本手冊採「新手可讀懂原理、專業人員可直接取用指令與程式碼」雙軌撰寫方式。

一、基本觀念（新手導讀）

1. 用白話比喻解釋 TLS／TLS 1.3／握手／加密套件

新手補充說明

把兩台電腦之間的通訊想像成「兩個人在公開的廣場上講悄悄話」。廣場上人來人往（網際網路），任何人都可能偷聽（竊聽）或假冒對方遞紙條（中間人攻擊）。TLS（Transport Layer Security）就是雙方在開口說真正的話之前，先用一套「暗號約定流程」確認彼此身分、約定好只有兩人看得懂的密語，之後所有對話都用這個密語加密。

握手（Handshake）就是「約定暗號」的過程：

  • 用戶端（Client）先說：「我懂這些暗號種類（Cipher Suite 清單），你選一個。」
  • 伺服器（Server）回覆：「好，我們用這一種，這是我的身分證明（憑證／Certificate）。」
  • 雙方各自算出一把只有彼此知道的鑰匙（透過金鑰交換演算法，例如 Diffie-Hellman）。
  • 之後的資料都用這把鑰匙加解密，外人即使攔截也只看到亂碼。

加密套件（Cipher Suite）是一整組演算法的組合，包含：金鑰交換演算法、身分驗證演算法、對稱加密演算法、雜湊演算法。TLS 1.3 大幅簡化了這組合，拿掉許多已知不安全的演算法（例如 RSA 金鑰交換、CBC 模式的加密、SHA-1）。

2. 為何要從舊版 TLS 升級到 1.3

面向TLS 1.0／1.1／1.2 的問題TLS 1.3 的改善
安全性存在已知弱點（BEAST、POODLE、Logjam 等），支援不安全的加密套件（RC4、3DES、CBC 模式）移除所有已知不安全演算法，只保留現代安全的 AEAD 加密套件（如 AES-GCM、ChaCha20-Poly1305）
Forward Secrecy（前向保密）TLS 1.2 可選用不具前向保密的 RSA 金鑰交換，一旦私鑰外洩，過去攔截的封包可被回溯解密強制使用 Ephemeral Diffie-Hellman，每次連線金鑰皆不同，私鑰外洩也無法回溯解密歷史流量
握手效能完整握手需要 2-RTT（來回兩次）完整握手縮短為 1-RTT；支援 0-RTT（Zero Round Trip Time）重連機制，進一步降低延遲
握手內容保護握手過程中憑證等資訊以明文傳輸握手後段內容（含伺服器憑證）已加密，減少可被觀察的資訊
操作步驟提示

本手冊的操作順序建議為：先確認現況（第二章）→ 依語言調整介接設定（第三章）→ 用腳本驗證（第四章）→ 遇到問題查第五章 → 上線前對照第六章清單。

3. 名詞速查表

名詞說明
TLSTransport Layer Security，傳輸層安全協定，用於加密網路通訊（HTTPS 即為 HTTP + TLS）
SSLTLS 的前身（Secure Sockets Layer），SSL 2.0／3.0 已被淘汰，現今常誤用「SSL」一詞泛指 TLS
Handshake（握手）用戶端與伺服器建立加密連線前，協商版本、加密套件、交換金鑰、驗證身分的過程
Cipher Suite（加密套件）握手後實際使用的一組加密演算法組合
Negotiated Protocol（協商結果）握手完成後雙方實際採用的 TLS 版本，此為驗證是否成功升級的關鍵欄位
Forward Secrecy（前向保密）即使長期私鑰外洩，過去的通訊內容也無法被回溯解密的特性
0-RTTTLS 1.3 提供的重連加速機制，允許用戶端在完成握手前就送出資料，需注意重放攻擊（Replay Attack）風險
JSSEJava Secure Socket Extension，Java 內建處理 TLS/SSL 的框架
SchannelWindows 作業系統內建的 TLS/SSL 實作元件，.NET Framework 在 Windows 上預設透過 Schannel 處理 TLS
CA（憑證授權機構）Certificate Authority，簽發並保證伺服器憑證真實性的第三方機構
ALPNApplication-Layer Protocol Negotiation，握手時順便協商上層應用協定（如 HTTP/2）

二、確認現況（升級前的盤點）

新手補充說明

升級前一定要先「盤點」：不知道現況就直接改設定，很容易改壞既有連線。這一章教你怎麼「看」，還不會動手改。

1. 確認作業系統底層是否支援 TLS 1.3

Linux（以 OpenSSL 版本為準）

TLS 1.3 需要 OpenSSL 1.1.1 以上版本（1.1.1 是第一個正式支援 TLS 1.3 的穩定版）。

# 查詢目前系統 OpenSSL 版本
openssl version -a
預期成功畫面
OpenSSL 3.0.2 15 Mar 2022 (Library: OpenSSL 3.0.2 15 Mar 2022)

只要版本號 大於等於 1.1.1，代表底層函式庫已支援 TLS 1.3。

常見失敗與提醒

若顯示 OpenSSL 1.0.2 或更舊版本，代表底層完全不支援 TLS 1.3，必須先升級作業系統套件（如 CentOS 7 內建的 1.0.2 就需要額外編譯或更換發行版）。

Windows（Schannel 支援版本）

操作步驟
  1. 確認 Windows 版本：winver 或 systeminfo | findstr /B /C:"OS"
  2. TLS 1.3（透過 Schannel）自 Windows 10 版本 1903 / Windows Server 2022 起才有原生支援；更早版本的 Schannel 不支援 TLS 1.3。
  3. 檢查登錄檔是否有停用 TLS 1.3（若企業有做安全性強化政策，路徑如下）：
reg query "HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.3"
提醒

Windows Server 2019 及更早版本的 Schannel 不支援 TLS 1.3，即使應用程式（如 .NET）宣稱支援，實際協商仍會失敗或退回 TLS 1.2，這一點在第三章 .NET 段落會再詳細說明。

2. 確認對接 AP Server 目前開放的 TLS 版本與加密套件

以下列出常見伺服器軟體「查詢目前設定」的方式（僅供查看，尚未涉及修改）：

伺服器設定檔／檢查方式查看重點
Nginxnginx -T | grep -i ssl_protocols確認 ssl_protocols 指令中是否含 TLSv1.3，Nginx 需 1.13.0 以上搭配 OpenSSL 1.1.1 以上才支援
Apache HTTPDapachectl -M | grep ssl 及檢查 SSLProtocol 指令需 Apache 2.4.37 以上搭配 OpenSSL 1.1.1 以上；確認 SSLProtocol 未排除 TLSv1.3
Tomcat檢查 server.xml 中 Connector 的 sslEnabledProtocols 屬性需 Tomcat 9.0.x（搭配 JDK 11 以上或 OpenSSL-based Connector）以上；純 JSSE 需底層 JDK 支援 TLS 1.3（JDK 11 以上原生支援）
IIS使用 reg query 檢查 Schannel 機碼，或用 Get-TlsCipherSuite（PowerShell）需 Windows Server 2022 以上，IIS 本身不單獨控制版本，完全依賴底層 Schannel
F5 BIG-IP於 GUI 查看 Local Traffic 到 Profiles 到 SSL 到 Client(Server)，或 tmsh list ltm profile client-ssl需 BIG-IP 版本 15.1 以上且授權含 TLS 1.3 支援，檢查 Cipher Group 是否含 TLS 1.3 相關套件
新手補充說明

如果你不是這台伺服器的管理者（例如你只是要串接對方的 API），你不需要登入對方主機，直接用下一節的 openssl s_client 或 nmap 從外部檢測即可，這是最常見也最實用的做法。

3. 使用 openssl s_client、curl、nmap 檢測遠端伺服器

方法一：openssl s_client（最常用，逐一指定版本測試）

操作步驟

將 example.com:443 換成實際要測試的主機與埠號：

# 測試是否可用 TLS 1.3 連線
openssl s_client -connect example.com:443 -tls1_3

# 測試是否仍可用 TLS 1.0（用來確認舊版是否已停用）
openssl s_client -connect example.com:443 -tls1
預期成功畫面（協商到 TLS 1.3）
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Server public key is 2048 bit
...
SSL-Session:
    Protocol  : TLSv1.3
    Cipher    : TLS_AES_256_GCM_SHA384

關鍵字：Protocol : TLSv1.3。只要看到這行，即代表此連線確實使用 TLS 1.3。

常見失敗畫面與原因
140177831907136:error:1409442E:SSL routines:ssl3_read_bytes:tlsv1 alert protocol version:...

代表伺服器不支援你指定的版本（此例為拒絕 TLS 1.0），通常是好事（代表舊版已停用）；但若指定 -tls1_3 卻出現此錯誤，代表伺服器尚未開放 TLS 1.3。

方法二：curl（模擬實際 API 呼叫情境）

# 強制以 TLS 1.3 呼叫，並顯示詳細握手過程
curl -v --tlsv1.3 --tls-max 1.3 https://example.com/api/health
預期成功畫面
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384
* Server certificate:
*  subject: CN=example.com
< HTTP/1.1 200 OK

關鍵字：SSL connection using TLSv1.3。

常見錯誤

curl: (35) OpenSSL/x.x.x: error:...unsupported protocol：通常代表本機 curl 所連結的 OpenSSL 版本過舊，或對方伺服器不支援 TLS 1.3。可先用 curl -V 確認 curl 連結的 SSL 函式庫版本。

方法三：nmap ssl-enum-ciphers（一次列出對方所有開放的版本與加密套件，適合稽核）

nmap --script ssl-enum-ciphers -p 443 example.com
預期輸出範例
443/tcp open  https
| ssl-enum-ciphers:
|   TLSv1.2:
|     ciphers:
|       TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 (secp256r1) - A
|   TLSv1.3:
|     ciphers:
|       TLS_AKE_WITH_AES_256_GCM_SHA384 (ecdh_x25519) - A
|     cipher preference: server
|_  least strength: A

此工具的優勢：一次列出「所有」開放版本，方便確認舊版（如 TLSv1、TLSv1.1）是否已經完全關閉，而不只是單點測試。

新手補充說明

如果輸出中完全沒有 TLSv1.3 這個區塊，代表對方伺服器目前根本沒開放 TLS 1.3，這種情況需要請對方（伺服器維運方）先行升級，不是你這邊改程式就能解決的。

三、開發語言介接設定與驗證

1. Java 專業

環境版本需求

JDK 版本TLS 1.3 支援狀況
JDK 8（小於等於 8u261）不支援
JDK 8u262 以上自 8u262 起回移（backport）支援 TLS 1.3，但預設仍以 TLS 1.2 為上限，需手動啟用
JDK 11 及以上原生支援，且預設協定清單已包含 TLSv1.3
特別提醒（JDK8 版號限制）

務必確認 JDK8 的實際小版號是否 大於等於 8u262，可用 java -version 查詢。低於此版號即使程式碼寫法完全正確，仍無法協商到 TLS 1.3。

設定方式：JVM 啟動參數

# 明確指定啟用的 TLS 版本（可放在啟動指令或 JAVA_OPTS）
-Dhttps.protocols=TLSv1.3
新手補充說明

這個參數只影響 Java 內建的 HttpsURLConnection 走 https.protocols 這個系統屬性的呼叫方式；若你的程式碼是自行建立 SSLContext（如下方範例），則要在程式碼裡指定，JVM 參數不一定會生效，兩者請擇一並確認實際生效的是哪一種。

程式碼範例：SSLContext 指定 TLS 1.3

import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLSocketFactory;
import javax.net.ssl.HttpsURLConnection;
import java.net.URL;

public class Tls13Client {
    public static void main(String[] args) throws Exception {
        // 建立指定 TLSv1.3 的 SSLContext
        SSLContext sslContext = SSLContext.getInstance("TLSv1.3");
        sslContext.init(null, null, null); // 使用預設信任庫與金鑰庫

        SSLSocketFactory factory = sslContext.getSocketFactory();

        URL url = new URL("https://example.com/api/health");
        HttpsURLConnection conn = (HttpsURLConnection) url.openConnection();
        conn.setSSLSocketFactory(factory);
        conn.connect();

        // 驗證是否真的協商到 TLS 1.3：印出 Negotiated Protocol
        System.out.println("Negotiated Protocol: " + conn.getCipherSuite());
        System.out.println("Response code: " + conn.getResponseCode());
    }
}

程式碼範例：直接以 SSLSocket 確認 Negotiated Protocol

import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSession;

public class Tls13SocketCheck {
    public static void main(String[] args) throws Exception {
        SSLContext sslContext = SSLContext.getInstance("TLSv1.3");
        sslContext.init(null, null, null);

        try (SSLSocket socket = (SSLSocket) sslContext.getSocketFactory()
                .createSocket("example.com", 443)) {
            socket.setEnabledProtocols(new String[]{"TLSv1.3"});
            socket.startHandshake();

            SSLSession session = socket.getSession();
            // 這裡印出的 Protocol 就是實際協商結果，是判斷成功與否的唯一依據
            System.out.println("Negotiated Protocol: " + session.getProtocol());
            System.out.println("Negotiated Cipher Suite: " + session.getCipherSuite());
        }
    }
}
預期成功輸出
Negotiated Protocol: TLSv1.3
Negotiated Cipher Suite: TLS_AES_256_GCM_SHA384
常見錯誤訊息與排除方法
錯誤訊息常見原因排除方法
SSLHandshakeException: No appropriate protocolJDK 版本過舊，不支援 TLSv1.3升級至 JDK 11 以上，或 JDK8u262 以上並確認啟用方式正確
SSLHandshakeException: Received fatal alert: protocol_version伺服器不支援 TLS 1.3，握手時被拒絕回到第二章確認伺服器端實際開放版本
PKIX path building failed與 TLS 版本無關，是憑證信任鏈問題（常被誤認為版本問題）檢查用戶端信任庫（cacerts）是否含對方憑證的根 CA

2. Python 專業

環境版本需求

元件需求版本
Python3.7 以上（3.7 起 ssl 模組正式支援 TLS 1.3）
底層 OpenSSLPython 直譯器編譯時所連結的 OpenSSL 需大於等於 1.1.1，可用下方指令確認
# 確認 Python 內建 ssl 模組連結的 OpenSSL 版本
python3 -c "import ssl; print(ssl.OPENSSL_VERSION)"
提醒

即使 Python 版本是 3.7 以上，若該 Python 是用舊版 OpenSSL（如 1.0.2）編譯而成（常見於某些較舊的 Linux 發行版內建 Python），仍然無法使用 TLS 1.3。這是最常被忽略的一點。

設定方式：ssl 模組直接使用

import ssl
import socket

context = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
context.minimum_version = ssl.TLSVersion.TLSv1_3  # 強制最低版本為 TLS 1.3
context.maximum_version = ssl.TLSVersion.TLSv1_3

with socket.create_connection(("example.com", 443)) as sock:
    with context.wrap_socket(sock, server_hostname="example.com") as ssock:
        # 驗證是否真的協商到 TLS 1.3
        print("Negotiated Protocol:", ssock.version())
        print("Negotiated Cipher:", ssock.cipher())
預期成功輸出
Negotiated Protocol: TLSv1.3
Negotiated Cipher: ('TLS_AES_256_GCM_SHA384', 'TLSv1.3', 256)

設定方式：requests 套件搭配自訂 HTTPAdapter

新手補充說明

requests 套件預設不會讓你直接指定 TLS 版本，需要透過自訂 HTTPAdapter，把剛剛設定好的 SSLContext 塞進去。

import ssl
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.ssl_ import create_urllib3_context

class TLS13Adapter(HTTPAdapter):
    def init_poolmanager(self, *args, **kwargs):
        context = create_urllib3_context()
        context.minimum_version = ssl.TLSVersion.TLSv1_3
        kwargs["ssl_context"] = context
        return super().init_poolmanager(*args, **kwargs)

session = requests.Session()
session.mount("https://", TLS13Adapter())

resp = session.get("https://example.com/api/health")
print("HTTP Status:", resp.status_code)

# 驗證實際協商版本：從底層 socket 取得
raw_sock = resp.raw._connection.sock  # 視 urllib3 版本，屬性名稱可能略有差異
print("Negotiated Protocol:", raw_sock.version())
常見錯誤訊息與排除方法
錯誤訊息常見原因排除方法
ssl.SSLError: [SSL: UNSUPPORTED_PROTOCOL]本機 OpenSSL 或伺服器不支援指定版本先用 python3 -c "import ssl; print(ssl.OPENSSL_VERSION)" 確認本機版本，再用第二章工具確認伺服器
AttributeError: module 'ssl' has no attribute 'TLSVersion'Python 版本低於 3.7升級 Python 至 3.7 以上
requests.exceptions.SSLError: certificate verify failed非版本問題，是憑證驗證失敗（常與 TLS 1.3 問題混淆）確認 certifi 套件版本與對方憑證鏈是否正確

3. .NET 專業

.NET Core／.NET 5+ 與 .NET Framework 4.8 的差異

項目.NET Core 3.1 / .NET 5 以上.NET Framework 4.8
TLS 1.3 支援原生支援（在支援的作業系統上）不支援應用層直接協商 TLS 1.3；完全依賴作業系統 Schannel
底層實作.NET Core 在 Windows 上仍使用 Schannel，在 Linux 上使用 OpenSSL僅能透過 Schannel
設定方式可在程式碼中以 SslProtocols.Tls13 明確指定幾乎無法在程式碼層級強制指定 TLS 1.3，需依賴 OS 更新與登錄檔設定
.NET Framework 特別提醒

在 .NET Framework 4.8 情境下，作業系統（Schannel）是否支援 TLS 1.3 才是關鍵：即使程式碼寫 SecurityProtocolType.Tls13，在不支援 TLS 1.3 的 Windows Server（如 2016、2019）上仍會拋出例外或直接被忽略。這是 .NET 介接最常見的誤解來源，請務必先完成第二章的 OS 檢查。

程式碼範例：.NET Core / .NET 5+（HttpClientHandler）

using System;
using System.Net.Http;
using System.Net.Security;
using System.Threading.Tasks;

class Program
{
    static async Task Main()
    {
        var handler = new HttpClientHandler
        {
            SslProtocols = SslProtocols.Tls13 // 明確指定僅使用 TLS 1.3
        };

        using var client = new HttpClient(handler);
        var response = await client.GetAsync("https://example.com/api/health");

        Console.WriteLine($"HTTP Status: {response.StatusCode}");
        // 注意：HttpClient 本身不直接暴露協商版本，
        // 若需要精確驗證，請改用下方 SslStream 寫法
    }
}

程式碼範例：以 SslStream 直接驗證 Negotiated Protocol

using System;
using System.Net.Sockets;
using System.Net.Security;
using System.Security.Authentication;

class TlsCheck
{
    static void Main()
    {
        using var client = new TcpClient("example.com", 443);
        using var sslStream = new SslStream(client.GetStream(), false);

        sslStream.AuthenticateAsClient(
            "example.com",
            null,
            SslProtocols.Tls13, // 僅允許 TLS 1.3，若協商失敗會直接拋出例外
            checkCertificateRevocation: true);

        // 驗證是否真的協商到 TLS 1.3
        Console.WriteLine($"Negotiated Protocol: {sslStream.SslProtocol}");
        Console.WriteLine($"Cipher Algorithm: {sslStream.CipherAlgorithm}, Strength: {sslStream.CipherStrength}");
    }
}

四、測試驗證腳本（可直接執行）

1. Linux Shell Script

操作步驟
  1. 建立檔案：vi check_tls13.sh，貼上下方內容並儲存
  2. 賦予執行權限：chmod +x check_tls13.sh
  3. 執行：./check_tls13.sh example.com 443
#!/bin/bash
# check_tls13.sh - 檢查目標主機 TLS 1.3 支援狀況與舊版協定是否已停用
# 用法：./check_tls13.sh <host> <port>

HOST=${1:-example.com}
PORT=${2:-443}

echo "=== 檢查 TLS 1.3 是否可連線 ==="
echo | openssl s_client -connect "${HOST}:${PORT}" -tls1_3 2>/dev/null | grep -E "Protocol|Cipher is"

echo ""
echo "=== 檢查 TLS 1.0 是否已停用（應該要失敗） ==="
echo | openssl s_client -connect "${HOST}:${PORT}" -tls1 2>&1 | grep -E "Protocol|alert|error" 

echo ""
echo "=== 檢查 TLS 1.1 是否已停用（應該要失敗） ==="
echo | openssl s_client -connect "${HOST}:${PORT}" -tls1_1 2>&1 | grep -E "Protocol|alert|error"

echo ""
echo "=== curl 實際 API 呼叫測試 ==="
curl -sv --tlsv1.3 --tls-max 1.3 "https://${HOST}:${PORT}/" 2>&1 | grep -E "SSL connection|HTTP/"
預期輸出判讀方式
  • 「檢查 TLS 1.3 是否可連線」區塊出現 Protocol : TLSv1.3 代表 TLS 1.3 可用
  • 「檢查 TLS 1.0／1.1 是否已停用」區塊出現 alert protocol version 或連線錯誤，代表舊版確實已停用（這是好結果）
  • 若「應該要失敗」的區塊反而顯示 Protocol : TLSv1，代表舊版協定尚未關閉，需要回頭調整伺服器設定

2. Windows Batch（.bat，需另行安裝 OpenSSL for Windows）

操作步驟
  1. 先安裝 OpenSSL for Windows（例如透過 Chocolatey：choco install openssl），並確認 openssl 指令已加入系統 PATH
  2. 用記事本建立 check_tls13.bat，貼上下方內容
  3. 雙擊執行，或於命令提示字元執行：check_tls13.bat example.com 443

常見失敗原因

若出現 'openssl' 不是內部或外部命令，代表 PATH 未設定成功，請確認安裝路徑（例如 C:\Program Files\OpenSSL-Win64\bin）已加入系統環境變數 PATH，並重新開啟命令提示字元。

3. Windows PowerShell（不需額外安裝任何工具）

操作步驟
  1. 以系統管理員身分開啟 PowerShell
  2. 若首次執行腳本被阻擋，先執行一次：Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
  3. 建立檔案 Check-Tls13.ps1，貼上下方內容
  4. 執行：.\Check-Tls13.ps1 -HostName example.com -Port 443
param(
    [string]$HostName = "example.com",
    [int]$Port = 443
)

function Test-TlsVersion {
    param([string]$Protocol)

    try {
        $tcpClient = New-Object System.Net.Sockets.TcpClient($HostName, $Port)
        $sslStream = New-Object System.Net.Security.SslStream($tcpClient.GetStream(), $false)

        $enum = [System.Security.Authentication.SslProtocols]::$Protocol
        $sslStream.AuthenticateAsClient($HostName, $null, $enum, $false)

        Write-Host "[$Protocol] 連線成功，實際協商版本：$($sslStream.SslProtocol)" -ForegroundColor Green

        $sslStream.Close()
        $tcpClient.Close()
    }
    catch {
        Write-Host "[$Protocol] 連線失敗：$($_.Exception.Message)" -ForegroundColor Yellow
    }
}

Write-Host "=== 檢查 TLS 1.3 是否可連線 ==="
Test-TlsVersion -Protocol "Tls13"

Write-Host ""
Write-Host "=== 檢查 TLS 1.0 是否已停用（應該要顯示失敗） ==="
Test-TlsVersion -Protocol "Tls"

Write-Host ""
Write-Host "=== 檢查 TLS 1.1 是否已停用（應該要顯示失敗） ==="
Test-TlsVersion -Protocol "Tls11"
預期輸出判讀方式
=== 檢查 TLS 1.3 是否可連線 ===
[Tls13] 連線成功，實際協商版本：Tls13

=== 檢查 TLS 1.0 是否已停用（應該要顯示失敗） ===
[Tls] 連線失敗：The client and server cannot communicate...

綠色訊息代表該版本可成功協商；黃色訊息代表連線失敗——對 TLS 1.3 而言黃色是壞消息，對 TLS 1.0／1.1 而言黃色反而是好消息（代表已停用）。

常見問題

若 PowerShell 版本或 .NET Framework 版本過舊，SslProtocols.Tls13 這個列舉值可能不存在，會出現找不到型別的錯誤，此時代表本機環境（用來執行檢測的這台電腦）本身就需要更新 .NET Framework 或 Windows 版本。

五、常見問題排除

1. 依角色分類的常見迷思

迷思一：「伺服器回應 200 OK，就代表用的是 TLS 1.3」

常見迷思澄清

錯誤。API 回應 200 OK 只代表「連線建立成功」，不代表協商版本一定是 TLS 1.3，伺服器可能同時開放 1.2 與 1.3，用戶端在未強制指定的情況下，可能被降級協商到 TLS 1.2 仍然成功回應。唯一正確的判斷方式，是實際印出 Negotiated Protocol（見第三章各語言範例），而不是看 HTTP 狀態碼。

依角色分類的排查方向

角色／情境常見狀況排查重點
伺服器不支援用戶端已正確設定，但握手時被拒絕或自動降版回到第二章，用 nmap／openssl s_client 直接對伺服器檢測，確認 TLS 1.3 是否真的有開放
用戶端版本過舊程式碼設定看似正確，卻始終協商不到 TLS 1.3檢查語言執行環境版本（JDK／Python／.NET）與底層函式庫（OpenSSL／Schannel）版本，見第三章「環境版本需求」
程式設定錯誤使用了看似正確但實際無效的參數（如只設 JVM 參數卻自建 SSLContext）確認程式碼中「實際生效」的設定路徑只有一個，避免多處設定互相打架
誤判連線成功即為 TLS 1.3看到 API 呼叫成功就結案，未實際檢查協商版本務必印出並記錄 Negotiated Protocol 欄位作為驗收證據

2. 現象／原因／處理對照表

現象可能原因處理方式
握手時直接被拒絕（connection reset）伺服器完全未開放 TLS 1.3；或防火牆／WAF 阻擋了特定 Cipher Suite用 nmap 確認伺服器實際開放版本；檢查中間是否有 WAF/Proxy 進行 TLS 終止（termination）
本機測試（openssl/curl）成功，但應用程式仍失敗應用程式使用的執行環境（JDK/Python/.NET Runtime）與本機命令列工具連結的函式庫不同確認應用程式實際執行時所用的 Runtime 版本與底層 TLS 函式庫版本，而非只看本機 CLI 工具版本
間歇性失敗（有時成功有時失敗）後端為多台伺服器組成的叢集，部分節點尚未完成 TLS 1.3 升級對叢集中每一個實際節點（而非只測 VIP／負載平衡器）分別執行第二章的檢測工具
憑證相關錯誤（誤以為是版本問題）憑證信任鏈、憑證過期、SNI 設定錯誤先確認錯誤訊息是否包含 certificate／PKIX 等字樣，這類錯誤與 TLS 版本無關，需另外排查憑證鏈
.NET Framework 環境始終無法使用 TLS 1.3作業系統 Schannel 版本過舊（如 Windows Server 2019 以前）需升級作業系統版本，應用程式層級無法繞過此限制

六、上線前檢查清單

使用方式

建議將此清單複製至內部工單或變更管理系統，逐項確認並保留每一項的檢測輸出畫面作為佐證。

  • 已使用 openssl version 或對應指令確認用戶端主機底層函式庫版本支援 TLS 1.3
  • 已使用 nmap --script ssl-enum-ciphers 或 openssl s_client 確認目標 API Server 已開放 TLS 1.3
  • 已確認目標 API Server 的 TLS 1.0／1.1（視公司政策，必要時含 1.2）已停用或訂有汰換計畫
  • Java／Python／.NET 各介接程式已於程式碼或設定中明確指定使用 TLS 1.3
  • 已於各語言環境中實際印出 Negotiated Protocol，並確認結果為 TLSv1.3／Tls13，而非僅以 HTTP 200 作為判斷依據
  • 已於 Linux 環境執行測試腳本並保留輸出紀錄
  • 已於 Windows 環境以 PowerShell（或搭配 OpenSSL 的 Batch）執行測試腳本並保留輸出紀錄
  • 已確認 .NET Framework 4.8 情境下，作業系統（Schannel）版本確實支援 TLS 1.3（如適用）
  • 已針對叢集／多節點架構，逐一節點完成檢測，而非僅測試負載平衡器 VIP
  • 已將本次升級的憑證信任鏈一併確認，排除「誤判為版本問題」的憑證相關錯誤
  • 已將所有測試指令、程式碼片段與輸出結果歸檔，作為稽核與回溯依據
  • 已規劃降版（Rollback）方案，若上線後發現既有舊系統無法相容 TLS 1.3 時的因應措施
